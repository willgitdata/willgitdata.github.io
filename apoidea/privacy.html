Two different things carry a privacy story and they are not the same, so they are separate below: this website, and a gateway deployment you sign into.

This website

It is a set of static files served by a 200-line node process with no dependencies. It has no analytics, no tag manager, no advertising pixel, no A/B framework and no embedded third-party script of any kind — a Content-Security-Policy served with every response forbids one from loading even if someone added it. It sets no cookies and reads none.

The pages make exactly three kinds of request, all of them optional and all of them visible in the source of apps/site:

  • /evals/*.json on this same origin — the measurement files every number on the site is rendered from.
  • GET /auth/me on the gateway origin, to decide whether the nav should say "Sign in" or "Open console". Your browser attaches the gateway's own session cookie if you already have one; the site itself cannot read that cookie (it is httpOnly) and learns only yes or no. If the gateway is unreachable the page carries on unchanged.
  • GET /v1/health on the gateway origin, for the "running live on this machine" banner. Same fail-soft rule.

The site server writes no access log — it logs one line, at startup, saying which port it bound. Whatever proxy or platform fronts it in a given deployment may keep logs of its own, and those are that operator's.

A gateway deployment

This is where anything personal lives, and it lives wherever the operator runs it — its own Postgres and its own object store. If you self-host, that is your infrastructure and no copy of it goes anywhere else. Apoideia's database is never a shared, vendor-hosted one: the gateway opens a connection to exactly one database, the one named by its own DATABASE_URL.

We hold no model-provider credentials

Verified against the source, not asserted. There is no call to any model provider's API anywhere in this repository's application code; the gateway carries no environment variable for an Anthropic or OpenAI key and no code that would read one; and the gateway makes exactly one outbound call in its entire surface — to the memory engine at APOIDEIA_MEMORY_URL.

The reason is structural rather than a policy we maintain: the model call happens inside your process. agent.wrap(client) proxies the client you constructed, holding the key you configured, and the request goes from your machine to your provider. A credential store for provider keys would be a secret we held and never used, so there is not one.

Sign-in and third parties

A deployment can be configured to verify sign-in through an external identity provider — in the v0.1 default hosted configuration, Supabase Auth. Where it is, that provider handles the password and the gateway receives only a signed token naming your user id; the gateway trusts that token's subject claim and nothing else in it. A self-hosted deployment with no such provider configured keeps the email and password hash in its own Postgres and talks to no third party at all.

Email is the only sign-in method in v0.1. There is no GitHub or Google sign-in, so no account of yours anywhere else is involved.

Access, export and deletion

v0.1 has no self-serve account deletion — that is a known gap rather than a policy. What exists today:

  • An agent's memories, lessons and runs can be exported over the API (GET /v1/agents/:slug/export).
  • Individual memories can be listed and deleted, and an agent can be deleted outright.
  • API keys can be revoked at any time, immediately.
  • If you self-host, deleting a row, a database or the whole deployment is entirely in your hands and needs nobody's cooperation.
  • If someone else operates the deployment you use, your request goes to them — they are the only party who can act on it.

Children

This is developer infrastructure. It is not directed at children and no account is intended for anyone under 16.
