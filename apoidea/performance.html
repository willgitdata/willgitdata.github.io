Against a real model MEASURED

One agent, one set of tasks, run twice through the same SDK and gateway — once with an empty memory, once with the firm's knowledge in it. Both arms run the same tasks, so the observations are paired and McNemar's exact test is the right instrument; comparing two independent confidence intervals would discard the pairing and with it the finding. Corroborating workloads

A single workload we wrote ourselves is the obvious objection to any result. These two answer it from different directions: one is an external corpus annotated by lawyers, the other removes the model from the measurement entirely.

The deterministic suite, in full

Every task family and every shape of agent work, cut both ways, including where we do worst. Its accuracy figure is not an accuracy claim about agents: the stub answers from the recalled cue and never opens a document, which is why rebuilding the entire workload so every document carried real content left this number unchanged to the decimal while the live numbers moved. What it measures exactly, with zero sampling noise, is the memory layer itself — its token and recall figures.

What measuring this changed

The first full run scored recall precision at 56%. That was not the workload being hard — it was two defects, and both are fixed in the numbers above:

  • Recall scored every matched word equally. A memory matching “the” ranked alongside one matching “subrogation”, so against a few hundred memories almost everything tied and the tie-break — recency — silently decided what got recalled. Ranking now weights each term by how rare it is in that agent's own store.
  • The wrapper asked memory about the wrong thing. It built its recall query from the last user message, which is right for a chat app and wrong for an agent loop: by step seven that message is a tool result, so memory was being asked about compute_exposure → total returned rather than the claim under investigation. It now asks about the task the run opened with, and recalls once per run instead of once per step.

Neither was visible from the old two-workload benchmark. Both were found by measuring against a store the size of a real one.

Two more, found the same way

  • Lessons were injected regardless of the question. Selection ranked by score and never looked at the query, so the top-scoring lessons went into every prompt whatever the task. That is the leading explanation for the one regression published above — on tasks needing no company-specific knowledge, the arm carrying memory scored worse than the arm carrying none. Irrelevant context is not free. Injection is relevance-gated now, and no relevant lesson means no injection.
  • A single memory was unrecallable. Term weighting used log((n+1)/(df+1)), which is exactly zero for a term appearing in every candidate — and with one memory, that is every term it contains. The tokens doing the matching were weighted to nothing. remember one fact and recall it came back empty: the first thing every new user does.

Both are fixed. The live figures above predate both fixes and are labelled with the commit they were measured at — re-running against a frontier model costs real money, so the numbers stay as measured until a re-run replaces them.
